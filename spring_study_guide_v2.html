🟩 무슨 뜻?

JPA가 Entity(자바 클래스)를 보고 DB 테이블 구조를 자동으로 맞춰주는 설정입니다. Entity에 필드를 추가하면 Hibernate가 알아서 테이블에 컬럼을 추가하려고 합니다. 수업에선 편해서 쓰지만…

🟥 운영 서버에서는 위험

update는 예측 못 한 테이블 변경을 일으킬 수 있어, 실제 서비스 운영 DB에선 데이터가 꼬이거나 사라질 위험이 있습니다. 그래서 운영에서는 보통 ddl-auto=none으로 두고 손댑니다.

Entity 관계 설계 — 이번 수업의 심장

게시판이 “게시판답게” 동작하려면 회원·게시글·댓글·첨부파일·좋아요가 서로 연결돼 있어야 합니다. 이 연결을 표현하는 게 Entity 관계입니다.

erDiagram MEMBER ||--o{ POST : "글을 쓴다" MEMBER ||--o{ COMMENT : "댓글을 쓴다" POST ||--o{ COMMENT : "댓글이 달린다" POST ||--o{ ATTACHMENT : "파일이 붙는다" POST ||--o{ POST_REACTION : "반응을 받는다" COMMENT ||--o{ COMMENT_REACTION : "반응을 받는다"
🟦 말로 풀면
  • 회원 1명은 게시글 여러 개를 쓸 수 있다
  • 게시글 1개에는 댓글 여러 개가 달릴 수 있다
  • 게시글 1개에는 첨부파일 여러 개가 붙을 수 있다
  • 회원 1명은 한 게시글에 좋아요/싫어요를 딱 하나만 누를 수 있다
🟨 “하나 대 여러 개” 읽는 법

다이어그램의 ||--o{ 기호에서 || 쪽이 “하나”, o{ 쪽이 “여러 개”입니다. 즉 회원(하나)과 게시글(여러 개)의 관계 = 일대다(One-to-Many)입니다.

06

JPA 핵심 어노테이션 (코드 한 줄씩)

🟦 JPA가 뭔가요?

JPA(Java Persistence API)는 “자바 객체를 DB 테이블처럼 다루게 해주는 약속”입니다. 원래는 SQL을 직접 써서 INSERT INTO member ...를 해야 하지만, JPA를 쓰면 memberRepository.save(member) 한 줄로 끝납니다. 그 구현체가 Hibernate입니다.

Member Entity 뜯어보기

Member.java
@Entity
@Table(name = "member")
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 20)
    private String username;

    @Column(nullable = false, length = 60)
    private String password;

    @Column(nullable = false, length = 20)
    private String nickname;

    @Column(nullable = false, length = 10)
    private String role = "USER";

    @Column(nullable = false, updatable = false, name = "created_at")
    private LocalDateTime createdAt;

    @PrePersist
    protected void onCreate() {
        this.createdAt = LocalDateTime.now();
    }
}
어노테이션한 줄 의미
@Entity이 클래스는 DB 테이블과 연결된다. (Member 객체 1개 = member 테이블의 1줄)
@Table(name="member")연결할 테이블 이름 지정
@Id이 필드가 기본키(PK), 즉 줄을 구분하는 고유 번호
@GeneratedValue(IDENTITY)MySQL의 AUTO_INCREMENT처럼 번호를 DB가 자동으로 매김
@Column(unique=true)이 컬럼 값은 중복 불가 (아이디 중복 방지)
@Column(nullable=false)비어있으면(null) 안 됨
@PrePersistDB에 처음 저장(INSERT)되기 직전에 자동 실행 → 가입 시각 자동 기록

Post와 Member의 관계 — @ManyToOne

Post.java (일부)
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "member_id", nullable = false)
private Member member;
🟩 왜 ManyToOne일까?

게시글 입장에서 생각해봅시다. “게시글 여러 개가 → 회원 한 명에게 속한다”. 그래서 게시글(다) 쪽에 @ManyToOne(다대일)이 붙습니다. @JoinColumn(name="member_id") 덕분에 post 테이블에 member_id라는 외래키(FK) 컬럼이 생깁니다.

post 테이블 ---- id title content member_id ← 누가 썼는지 가리키는 외래키

Post와 Comment의 관계 — @OneToMany & mappedBy

Post.java
@OneToMany(
    mappedBy = "post",
    cascade = CascadeType.ALL,
    orphanRemoval = true,
    fetch = FetchType.LAZY
)
private List<Comment> comments = new ArrayList<>();
Comment.java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(nullable = false, name = "post_id")
private Post post;
🟨 mappedBy가 제일 헷갈려요

mappedBy="post"는 “이 관계의 진짜 주인은 Comment의 post 필드”라는 표시입니다. 규칙은 간단합니다: 외래키(post_id)를 가진 쪽이 주인입니다. comment 테이블에 post_id가 있으니 주인은 Comment.post이고, Post.comments는 그냥 “반대편에서 편하게 보려는 목록”일 뿐입니다.

cascade와 orphanRemoval

옵션의미예시
cascade = ALL부모 작업을 자식에게 전파게시글 삭제 → 댓글·첨부파일도 함께 삭제
orphanRemoval = true부모와 연결이 끊긴 자식을 DB에서도 제거리스트에서 댓글 빼면 → DB 댓글도 삭제
🟥 주의

cascade=ALL은 강력한 만큼 위험합니다. 게시글 하나 지웠는데 의도치 않게 수백 개 자식 데이터가 같이 날아갈 수 있으니, 정말 “부모-자식이 생사를 같이 하는 관계”일 때만 쓰세요.

🟪 요즘 트렌드

최신 자바·Spring에서는 Entity를 record나 불변(immutable) 스타일로 만들거나, Lombok 대신 JPA Buddy 같은 도구로 보일러플레이트를 줄이는 흐름이 있습니다. 또 연관관계는 가능한 한 단방향(한쪽만)으로 단순하게 두는 것을 권장하는 분위기입니다.

N+1 문제와 Fetch Join

🟦 FetchType.LAZY 복습

게시글을 조회할 때 작성자 정보까지 바로 가져오지 말고, “진짜 member가 필요해지는 순간”에 가져오라는 게 LAZY(지연 로딩)입니다. 평소엔 불필요한 조회를 줄여 좋지만… 목록에서 작성자 닉네임을 매번 보여줘야 한다면 문제가 생깁니다.

N+1 문제가 뭔가요?

게시글 목록 10개 조회 → 쿼리 1번 각 게시글의 작성자 닉네임 조회 → 쿼리 10번 ───────────────────────────────── 총 11번 😱
🟥 이것이 N+1

목록 1번 + 각 항목마다 N번 추가 쿼리 = 1 + N번. 게시글이 100개면 101번, 1000개면 1001번 DB를 두드립니다. 화면은 멀쩡해 보여도 서버는 비명을 지릅니다.

해결: Fetch Join

PostRepository.java
@Query(
    value = "select p from Post p join fetch p.member order by p.id desc",
    countQuery = "select count(p) from Post p"
)
Page<Post> findAllWithPost(Pageable pageable);
🟩 핵심 한 줄

join fetch p.member = “게시글을 가져올 때 작성자 Member도 한 방의 쿼리로 같이 가져와라”. 그러면 목록 화면에서 post.member.nickname을 써도 추가 쿼리가 거의 안 나갑니다. 11번이 → 1번으로 줄어듭니다.

🟨 countQuery는 왜 따로?

페이징은 “전체가 몇 개인지”도 알아야 합니다. 그런데 개수를 셀 때는 join fetch가 필요 없고 오히려 방해되므로, 개수 세는 쿼리는 따로 분리해 둡니다.

⬜ 다른 해결법
  • @EntityGraph — 어노테이션만으로 Fetch Join과 비슷한 효과
  • Batch Size 설정 — N+1을 1+1로 줄이는 hibernate.default_batch_fetch_size
  • DTO 직접 조회(Projection) — 필요한 컬럼만 골라 가져오기 (가장 가벼움)

DTO와 입력 검증(Validation)

🟦 Entity vs DTO

Entity는 DB용 객체, DTO는 화면 입력/출력용 객체입니다. 회원가입 폼에서 들어온 값을 곧장 Entity에 담지 않고, 일단 DTO라는 안전한 그릇에 받습니다. 이렇게 분리하면 DB 구조가 외부에 노출되지 않고, 검증 규칙도 깔끔하게 붙일 수 있습니다.

MemberDTO.java — 회원가입 폼용
public class MemberDTO {

    @NotBlank(message = "아이디를 입력해 주세요")
    @Size(min = 4, max = 20, message = "아이디는 4~20 글자")
    @Pattern(regexp = "^[a-zA-Z0-9_]+$", message = "영문, 숫자, _ 만 가능")
    private String username;

    @NotBlank(message = "비밀번호를 입력해 주세요")
    @Size(min = 6, message = "비밀번호는 6글자 이상")
    private String password;

    @NotBlank(message = "닉네임을 입력해 주세요")
    @Size(min = 4, max = 10, message = "닉네임은 4~10 글자")
    private String nickname;
}
검증 어노테이션의미
@NotBlank빈 값·공백만 있으면 거부
@Size(min, max)글자 수 범위 제한
@Pattern(regexp)정규식 규칙에 맞는 글자만 허용
🟩 검증이 동작하는 흐름

컨트롤러에서 @Valid를 붙이면 위 규칙이 자동 실행되고, 어긴 내용은 BindingResult에 담깁니다. 개발자는 bindingResult.hasErrors()로 “문제 있나?”만 확인하면 됩니다.

검증 결과 받기 — 순서가 중요!
@Valid @ModelAttribute("form") MemberDTO form,
BindingResult bindingResult   // 반드시 검증 대상 "바로 뒤"에
🟥 자주 하는 실수

BindingResult는 반드시 @Valid 대상 바로 다음 자리에 와야 합니다. 사이에 다른 파라미터가 끼면 검증 오류가 화면으로 안 잡히고 곧장 예외가 터집니다.

응답용 DTO 예시 — ReactionDTO

좋아요/싫어요 API 응답
{
  "likes": 3,
  "dislikes": 1,
  "myReaction": null
}
🟪 요즘 트렌드

자바 16+에서는 DTO를 record로 만드는 게 대세입니다. public record ReactionDTO(Long likes, Long dislikes, String myReaction){} 한 줄이면 끝 — getter·생성자가 자동 생성됩니다. 코드가 훨씬 짧고 불변이라 안전합니다.

회원가입 & 비밀번호 암호화

회원가입 흐름

GET /auth/register → 회원가입 화면(빈 폼) POST /auth/register → 검증 → 중복확인 → 암호화 → 저장 → 로그인 페이지로
AuthController.java
@PostMapping("/register")
public String register(
        @Valid @ModelAttribute("form") MemberDTO form,
        BindingResult bindingResult,
        RedirectAttributes redirectAttributes
) {
    if (bindingResult.hasErrors()) {
        return "auth/register";          // 검증 실패 → 다시 폼으로
    }
    try {
        memberService.register(form);
        redirectAttributes.addFlashAttribute("message", "회원가입 완료!");
        return "redirect:/auth/login";
    } catch (IllegalArgumentException e) {
        bindingResult.reject(e.getMessage());
        return "auth/register";
    }
}

비밀번호 암호화 — BCrypt

🟦 왜 암호화하나?

비밀번호를 그대로 DB에 저장하면, DB가 유출됐을 때 모든 사용자의 비번이 통째로 털립니다. 그래서 알아볼 수 없는 형태(해시)로 바꿔 저장합니다. BCrypt는 이 용도로 가장 널리 쓰이는 해시 알고리즘입니다.

MemberService.java
private final PasswordEncoder passwordEncoder = new BCryptPasswordEncoder(10);

// 회원가입 시: 평문 → 해시 → 저장
member.setPassword(passwordEncoder.encode(form.getPassword()));

// 로그인 시: 입력값과 저장된 해시를 "matches"로 비교
if (!passwordEncoder.matches(password, member.getPassword())) {
    throw new IllegalArgumentException("아이디 또는 비밀번호가 올바르지 않습니다.");
}
평문 비밀번호 → BCrypt 해시 → DB 저장 "123456" → "$2a$10$N9qo8uLO..."
🟥 절대 이렇게 비교하지 마세요
// ❌ 잘못된 비교
passwordEncoder.encode(password).equals(member.getPassword())

BCrypt는 매번 다른 소금(salt)을 섞어서, 같은 비밀번호라도 해시 결과가 매번 달라집니다. 그래서 encode 후 equals로 비교하면 항상 실패합니다. 반드시 matches(평문, 해시)를 써야 내부적으로 소금을 풀어 올바르게 비교합니다.

🟨 알고리즘 한 스푼

BCryptPasswordEncoder(10)의 숫자 10은 강도(cost factor)입니다. 숫자가 1 오를 때마다 계산량이 2배가 됩니다. 일부러 느리게 만들어, 공격자가 비밀번호를 무차별 대입(brute force)하기 어렵게 만드는 게 핵심 아이디어입니다.

🟪 요즘 트렌드

BCrypt는 여전히 훌륭하지만, 더 최신 환경에서는 메모리까지 많이 쓰게 만들어 GPU 공격에 강한 Argon2나 scrypt를 권장하기도 합니다. Spring Security는 DelegatingPasswordEncoder로 여러 방식을 동시에 지원합니다.

로그인 & 세션 (step14 방식)

🟦 세션이란?

세션은 “로그인 상태를 서버가 기억하는 사물함”입니다. 로그인에 성공하면 서버가 사물함에 회원 정보를 넣어두고, 사용자에게는 사물함 열쇠(세션 ID 쿠키)를 줍니다. 이후 요청마다 이 열쇠를 보여주면 서버가 “아, 로그인한 사람이구나” 알아봅니다.

AuthController.java
@PostMapping("/login")
public String login(String username, String password,
                    HttpSession session,
                    RedirectAttributes redirectAttributes) {
    try {
        Member member = memberService.login(username, password);
        session.setAttribute("loginMember", member);   // 사물함에 저장
        return "redirect:/board";
    } catch (Exception e) {
        redirectAttributes.addFlashAttribute("errorMessage",
                "아이디 또는 비밀번호가 올바르지 않습니다.");
        return "redirect:/auth/login";
    }
}

이후 다른 컨트롤러에서는 이렇게 꺼내 씁니다:

@SessionAttribute("loginMember") Member loginMember

로그아웃

@GetMapping("/logout")

    session.invalidate();   // 사물함 통째로 비우기
    return "redirect:/board";
}
🟪 트렌드 미리보기

세션 방식은 서버가 상태를 기억해야 해서, 서버를 여러 대로 늘리면 “누가 어느 서버에 로그인했는지” 공유 문제가 생깁니다. 그래서 요즘 API 서버·앱·React 환경에서는 서버가 상태를 안 가지는 JWT 토큰 방식으로 많이 넘어갑니다 — 바로 다음 PART 2의 주제입니다.

게시글 CRUD 전체 흐름

CRUD는 Create(생성)·Read(조회)·Update(수정)·Delete(삭제)의 약자, 즉 데이터 다루기의 기본 4동작입니다.

목록 조회 + 페이징

PostController.java
@GetMapping
public ModelAndView list(ModelAndView view,
        @RequestParam(defaultValue = "") String keyword,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "10") int size) {

    Pageable pageable = PageRequest.of(page, size);
    Page<Post> list = postService.getPostList(keyword, pageable);

    view.addObject("postPage", list);
    view.addObject("keyword", keyword);
    view.setViewName("board/list");
    return view;
}
🟩 페이징 원리

PageRequest.of(page, size) = “page번째 페이지에서 size개씩 가져와라”. 한 번에 1000개를 다 불러오면 느리니까, 10개씩 잘라서 보여주는 겁니다.

  • of(0, 10) → 첫 페이지, 10개 (페이지는 0부터 시작!)
  • of(1, 10) → 두 번째 페이지, 10개
🟨 Page 객체는 똑똑하다

결과로 받는 Page<Post>에는 글 목록뿐 아니라 isFirst(), isLast(), getTotalPages() 같은 페이지 정보가 다 들어있어, 화면에서 “이전/다음” 버튼을 쉽게 만들 수 있습니다.

검색

PostService.java
public Page<Post> getPostList(String keyword, Pageable pageable) {
    if (keyword == null || keyword.isEmpty()) {
        return postRepository.findAllWithPost(pageable);     // 전체
    } else {
        return postRepository.searchWithPost(keyword, pageable); // 검색
    }
}
검색 조건: 게시글 제목에 keyword 포함 OR 작성자 닉네임에 keyword 포함

글 작성 (로그인 필수)

POST /board/new → 로그인 확인 (안 했으면 로그인 페이지로) → 제목/내용 검증 → PostService.createPost() (게시글 저장) → AttachmentService.saveFiles() (첨부파일 저장) → redirect
PostService.createPost()
@Transactional
public Post createPost(PostFormDTO form, Member loginMember) {
    Post post = new Post();
    post.setTitle(form.getTitle());
    post.setContent(form.getContent());
    post.setMember(loginMember);
    postRepository.save(post);     // INSERT
    return post;
}
🟩 @Transactional이 왜?

게시글 등록은 DB에 “쓰는” 작업입니다. @Transactional이 붙으면 메서드가 정상적으로 끝날 때만 DB에 반영(commit)되고, 중간에 예외가 터지면 전부 되돌립니다(rollback). “전부 성공 or 전부 취소” — 데이터를 반쪽짜리로 남기지 않는 안전장치입니다.

🟥 GET으로 삭제하는 문제

예제에서는 이해하기 쉽게 @GetMapping("/{id}/delete")로 삭제합니다. 하지만 실무에선 GET 삭제는 금물입니다 — 검색엔진 크롤러나 미리보기가 링크를 자동으로 따라가면서 글을 지워버릴 수 있기 때문입니다.

⬜ 다른 방법 (실무 표준)

삭제는 @PostMapping 또는 REST API라면 @DeleteMapping을 씁니다. 동작의 의미와 HTTP 메서드를 일치시키는 게 원칙입니다 (조회=GET, 생성=POST, 수정=PUT/PATCH, 삭제=DELETE).

파일 업로드

🟦 파일은 두 군데에 나눠 저장

업로드한 파일은 실제 파일은 서버 폴더에, 파일 정보(이름·크기 등)는 DB에 나눠 저장합니다. DB에 파일 자체(이미지 덩어리)를 넣으면 DB가 무거워지기 때문입니다.

저장 위치저장 내용
서버 폴더 (uploads/)실제 파일 데이터
DB attachment 테이블원본 파일명, 저장 파일명, 크기, 게시글 ID

원본 이름 ≠ 저장 이름

🟩 왜 이름을 둘로 나누나?

사용자 A도 image.png, 사용자 B도 image.png를 올리면 같은 이름이라 덮어쓰기 사고가 납니다. 그래서 실제 저장 이름은 절대 겹치지 않는 UUID(랜덤 고유값)로 바꿔 저장하고, 원래 이름은 따로 기록해 둡니다.

originalName = image.png (사용자에게 보여줄 이름) storedName = a1b2c3-...-.png (서버에 실제 저장될 고유 이름)
AttachmentService — 파일 저장
String originalName = file.getOriginalFilename();
String extension = "";
if (originalName != null && originalName.contains(".")) {
    extension = originalName.substring(originalName.lastIndexOf("."));
}
String storedName = UUID.randomUUID() + extension;     // 고유 이름 생성

Files.copy(file.getInputStream(), uploadPath.resolve(storedName)); // 실제 저장

// DB에는 정보만
Attachment attachment = new Attachment();
attachment.setOriginalName(originalName);
attachment.setStoredName(storedName);
attachment.setFileSize(file.getSize());
attachment.setPost(post);
attachmentRepository.save(attachment);
🟥 삭제할 때 둘 다 챙기기

게시글을 지울 때 DB의 attachment 줄만 지우면 실제 파일은 폴더에 좀비처럼 남습니다. 반대로 파일만 지우면 DB에 깨진 기록이 남습니다. 그래서 삭제 시 ①실제 파일 ②DB 기록을 모두 지워야 합니다.

🟪 요즘 트렌드

실무에선 파일을 서버 로컬 폴더가 아니라 AWS S3 같은 클라우드 스토리지에 올립니다. 서버를 늘리거나 재배포해도 파일이 안 사라지고, CDN으로 빠르게 전송할 수 있기 때문입니다.

조회수 중복 방지 & Dirty Checking

새로고침할 때마다 조회수가 오르면 안 되니까

🟦 아이디어

세션에 “이 사용자가 이미 본 게시글 ID 목록”을 저장해 둡니다. 처음 보는 글이면 +1, 이미 본 글이면 그대로 둡니다.

PostController.detail() 일부
HashSet<Long> pageList = (HashSet<Long>) session.getAttribute("pageList");
if (pageList == null) {
    pageList = new HashSet<>();
    session.setAttribute("pageList", pageList);
}
if (pageList.add(id)) {        // 처음 보는 글이면 true
    postService.updateCount(id);   // 조회수 +1
}
🟨 왜 HashSet인가? (자료구조 선택)

HashSet은 중복을 허용하지 않는 자료구조입니다. add()가 똑똑한 신호를 줍니다: 처음 넣으면 true, 이미 있으면 false. 이 한 줄로 “처음인가?”를 판단할 수 있어 코드가 아주 깔끔해집니다. 게다가 조회(있나 없나)가 평균 O(1)로 매우 빠릅니다.

조회수 +1 코드에 save()가 없다?!

PostService.java
@Transactional
public void updateCount(Long id) {
    Post post = findById(id);
    post.setViewCount(post.getViewCount() + 1);
    // ⚠️ save()를 부르지 않는다!
}
🟩 Dirty Checking (변경 감지)

JPA의 마법 같은 기능입니다. 트랜잭션 안에서 조회한 Entity는 영속성 컨텍스트가 “원래 값”을 기억해 둡니다. 그리고 트랜잭션이 끝날 때 “어? 값이 바뀌었네(dirty)?” 하고 자동으로 비교해서 바뀐 부분만 UPDATE 쿼리를 날립니다. 그래서 save()를 직접 부를 필요가 없습니다.

트랜잭션 시작 → Post 조회 (영속성 컨텍스트가 원래 값 기억) → post.viewCount 변경 → 트랜잭션 종료 시 변경 감지 → UPDATE 쿼리 자동 실행 ✨
🟥 단, 조건이 있다

Dirty Checking은 ①Entity가 영속 상태이고 ②트랜잭션 안일 때만 작동합니다. 트랜잭션이 끝난 뒤 값을 바꾸면 아무 일도 안 일어납니다. 그래서 수정 메서드엔 @Transactional이 꼭 필요합니다.

🟩 UniqueConstraint

ReactionType은 왜 enum?

🟨 enum의 장점

PART 2 — 세션 인증 vs JWT 인증

step14는 세션으로 로그인을 기억했습니다. step15부터는 JWT라는 토큰으로 인증합니다. React 같은 프론트엔드와 연동하기 좋은 방식입니다.

🟦 JWT가 뭔가요?

JWT(JSON Web Token)는 “위조 불가능한 신분증” 같은 문자열입니다. 로그인에 성공하면 서버가 이 신분증을 발급해 주고, 사용자는 이후 요청마다 신분증을 내밉니다. 서버는 신분증의 서명만 확인하면 되므로, 누가 로그인했는지 따로 기억(세션)할 필요가 없습니다.

로그인 성공 → 서버가 JWT 발급 → 프론트가 JWT 저장 → API 요청마다 Authorization 헤더에 JWT 첨부 → 서버가 매 요청마다 JWT 서명 검증
구분세션 방식 (step14)JWT 방식 (step15)
로그인 상태 저장서버 메모리(세션)클라이언트(토큰)
요청 시 인증세션 쿠키 확인Authorization 헤더 확인
서버 상태상태 있음(stateful)무상태(stateless)에 가까움
로그아웃세션 삭제Refresh Token 삭제 + Access Token 만료 대기
서버 확장세션 공유 필요(번거로움)서버 늘리기 쉬움

JWT의 생김새 — 점 두 개로 나뉜 3조각

eyJhbGc... . eyJzdWI... . SflKxwRJ... 헤더(Header) 내용(Payload) 서명(Signature)
🟥 Payload는 암호화가 아니다!

JWT의 내용(payload)은 그냥 Base64로 인코딩된 것일 뿐, 누구나 풀어볼 수 있습니다. 그래서 비밀번호 같은 민감 정보는 절대 넣으면 안 됩니다. 서명(signature)은 “내용이 위조되지 않았음”만 보장하지, 내용을 숨겨주지 않습니다.

@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {
    private final JwtAuthenticationFilter jwtAuthenticationFilter;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
          .csrf(csrf -> csrf.disable())
          .cors(cors -> cors.configurationSource(corsConfigurationSource()))
          .sessionManagement(sm ->
              sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
          .authorizeHttpRequests(auth -> auth
              .requestMatchers("/auth/**").permitAll()
              .requestMatchers(HttpMethod.GET, "/api/posts/**").permitAll()
              .anyRequest().authenticated()
          )
          .addFilterBefore(jwtAuthenticationFilter,
              UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}

Access Token 생성

JwtTokenProvider.java
public String generateAccessToken(UserDetails details) {
    String role = details.getAuthorities().stream()
            .findFirst()
            .map(GrantedAuthority::getAuthority)
            .orElse("ROLE_USER");

    return Jwts.builder()
            .subject(details.getUsername())   // 누구인지
            .claim("role", role)              // 권한
            .issuedAt(new Date())             // 발급 시각
            .expiration(new Date(System.currentTimeMillis() + accessExpiration))
            .signWith(secretKey)              // 서버 비밀키로 서명
            .compact();
}
🟩 토큰에 담기는 것
  • subject: username (누구의 토큰인가)
  • role: ROLE_USER 같은 권한
  • issuedAt / expiration: 발급·만료 시각
  • signature: 서버 비밀키로 만든 서명 (위조 방지 도장)

private String extractToken(HttpServletRequest request) {
    String header = request.getHeader("Authorization");
    if (header != null && header.startsWith("Bearer ")) {
        return header.substring(7);   // "Bearer " 7글자 제거
    }
    return null;
}

UserDetails & 로그인 처리

🟦 UserDetails란?

Spring Security가 “로그인한 사용자”를 이해하기 위한 표준 규격(인터페이스)입니다. username, password, authorities(권한) 세 가지를 요구합니다. 우리 UserEntity가 이 규격을 구현하면, DB에서 꺼낸 객체를 그대로 인증 사용자로 쓸 수 있습니다.

UserEntity.java
@Entity
@Table(name = "users")
public class UserEntity implements UserDetails {   // ← 규격 구현
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false, length = 50)
    private String username;
    @Column(nullable = false, length = 255)
    private String password;

Refresh Token — 로그아웃의 비밀

AuthService.java
private void saveRefreshToken(UserEntity user, String refreshToken) {
    refreshTokenRepository.deleteByUser(user);   // 기존 것 삭제

    RefreshToken token = new RefreshToken();
    token.setToken(refreshToken);
    token.setUser(user);
    token.setExpiresAt(LocalDateTime.now().plusDays(7));
    refreshTokenRepository.save(token);
}
🟦 왜 Refresh Token을 DB에 저장?

Access Token은 서버에 저장하지 않습니다(무상태). 그래서 이미 발급된 Access Token을 서버가 강제로 무효화하기 어렵습니다. 대신 Refresh Token을 DB에 저장해두고, 로그아웃하면 이 Refresh Token을 DB에서 지웁니다.

로그아웃 = Refresh Token 삭제 → 새 Access Token 재발급을 막는다 → 기존 Access Token은 짧은 만료시간(30분) 지나면 자연히 죽음
🟩 두 토큰을 나눈 이유

Access Token을 길게 잡으면 탈취당했을 때 위험이 큽니다. 그래서 Access는 짧게(30분) 두어 위험을 줄이고, 만료되면 Refresh로 조용히 재발급받아 사용자가 자꾸 다시 로그인하지 않게 합니다. 보안과 편의의 절충입니다.

🟪 요즘 트렌드

Refresh Token을 더 안전하게 HttpOnly 쿠키로 내려주거나, 한 번 쓰면 새 토큰으로 바꿔주는 Refresh Token Rotation 기법, 또는 아예 Redis에 토큰 블랙리스트를 두는 방식이 많이 쓰입니다.

PART 3 — OAuth2 전체 흐름

🟦 OAuth2가 뭔가요?

“구글로 로그인”, “카카오로 로그인” 버튼이 바로 OAuth2입니다. 우리 서비스가 사용자의 비밀번호를 직접 받지 않고, 구글에게 “이 사람 맞는지 대신 확인해줘”라고 위임하는 표준입니다. 사용자는 비번을 우리에게 안 줘서 안전하고, 우리는 회원가입 절차가 간단해집니다.

🟨 authorization code가 뭐죠?

CustomOAuth2UserService.java
@Transactional @Override
public OAuth2User loadUser(OAuth2UserRequest userRequest) {
    OAuth2User oAuth2User = delegate.loadUser(userRequest);

    String provider   = userRequest.getClientRegistration().getRegistrationId();
    String email      = oAuth2User.getAttribute("email");
    String providerId = oAuth2User.getAttribute("sub");
    String name       = oAuth2User.getAttribute("name");

    userRepository.findByEmail(email).orElseGet(() -> {
        UserEntity newUser = new UserEntity();
        newUser.setUsername(name);
        newUser.setEmail(email);
        newUser.setProvider(provider);
        newUser.setProviderId(providerId);
        return userRepository.save(newUser);   // 처음이면 자동 가입
    });
    return oAuth2User;
}
🟩 자동 회원가입 로직

findByEmail(email).orElseGet(...) = “이미 가입된 이메일이면 그대로 쓰고, 처음 보는 이메일이면 새 회원으로 저장”. 사용자는 따로 회원가입 폼을 채울 필요 없이, 구글 로그인 한 번으로 가입과 로그인이 동시에 됩니다. delegate는 구글 사용자 정보 API 호출을 Spring 기본 구현에 맡기는 부분입니다.

🟥 가장 중요한 개념: 두 토큰은 다르다

OAuth2 과정에서 생기는 구글 Access Token은 “구글 API를 호출하기 위한” 토큰입니다. 우리 백엔드 API 인증에는 쓸 수 없습니다. 우리 API는 우리 서비스 JWT를 요구합니다. 그래서 구글 로그인 성공 후, 우리 토큰을 새로 발급해줘야 합니다.

두 가지 DB 접근 기술을 역할에 따라 나눠 동시에 씁니다. “어떤 기술이 더 좋다”가 아니라 “어디에 무엇이 더 어울리나”를 보여주는 구성입니다.

기술맡은 부분이유
JPA회원, Refresh Token (UserEntity, RefreshToken + Repository)단순 저장·단건 조회는 코드가 짧고 편리
MyBatis게시글·댓글·검색·페이징 (BoardMapper + XML)복잡한 JOIN·집계·페이징 SQL을 눈으로 직접 확인·제어

JPA가 빛나는 순간 (간단한 조회·저장)

userRepository.findByUsername(username);
userRepository.save(user);
refreshTokenRepository.deleteByUser(user);

메서드 이름만으로 SQL이 자동 생성됩니다. 짧고 명확합니다.

MyBatis가 빛나는 순간 (복잡한 SQL)

회원 테이블 JOIN 게시글 좋아요/싫어요 개수 집계 ROW_NUMBER()를 이용한 페이징 제목 또는 내용 검색 게시글별 댓글 조회
🟩 정리

이런 SQL은 자바 메서드 이름만으로 만들기 어렵고, 자동 생성된 쿼리는 성능 튜닝도 까다롭습니다. MyBatis XML에 직접 쓰면 SQL 흐름이 한눈에 보이고 자유롭게 다듬을 수 있습니다.

🟪 트렌드

실무에서도 JPA를 기본으로 쓰되, 통계·리포트·복잡한 검색처럼 손이 많이 가는 쿼리는 MyBatis나 QueryDSL로 보완하는 “혼합 전략”이 흔합니다. 무리해서 한 기술만 고집하지 않는 게 요령입니다.

board_view를 만든 이유 — 복잡한 조회를 미리 포장

🟦 View(뷰)란?

여러 테이블을 JOIN·집계한 결과에 이름을 붙여 가상의 테이블처럼 쓰는 기능입니다. 목록 화면엔 게시글 값 + 작성자 닉네임 + 좋아요/싫어요 개수가 다 필요한데, 매번 긴 JOIN을 쓰면 SQL이 지저분해집니다. 그래서 한 번 만들어 두고 SELECT * FROM board_view로 간단히 꺼냅니다.

board.sql — board_view (요약)
CREATE OR REPLACE VIEW board_view AS
WITH board_content_like AS (        -- CTE: 좋아요 개수 집계
    SELECT br.bno, COUNT(*) AS blike
    FROM board_reaction br WHERE br.type = 'like' GROUP BY br.bno
),
board_content_hate AS (             -- CTE: 싫어요 개수 집계
    SELECT br.bno, COUNT(*) AS bhate
    FROM board_reaction br WHERE br.type = 'dislike' GROUP BY br.bno
)
SELECT b.bno, b.title, b.write_date, b.content, b.bcount,
       bm.id AS mid, bm.nickname,
       IFNULL(bcl.blike, 0) AS blike,
       IFNULL(bch.bhate, 0) AS bhate
FROM board b
LEFT OUTER JOIN board_member bm        ON b.mid = bm.id
LEFT OUTER JOIN board_content_like bcl ON bcl.bno = b.bno
LEFT OUTER JOIN board_content_hate bch ON bch.bno = b.bno;
문법의미
WITH ... AS (...) (CTE)긴 SQL 안에서 임시 결과에 이름을 붙이는 문법. 가독성↑
LEFT OUTER JOIN좋아요 0개인 글도 목록에서 사라지지 않게 — 반응 없어도 게시글은 나옴
IFNULL(x, 0)집계 결과가 NULL이면 0으로 바꿔 줌
🟨 LEFT JOIN을 쓰는 이유 (한 번 더)

그냥 JOIN(=INNER JOIN)을 쓰면 좋아요 기록이 없는 게시글은 결과에서 통째로 빠집니다. 새 글은 좋아요가 0개니까요. 그래서 “왼쪽(게시글)은 무조건 남긴다”는 LEFT JOIN이 꼭 필요합니다.

ROW_NUMBER 기반 페이징 SQL

step14는 JPA의 Pageable이 페이징을 자동 처리했지만, MyBatis에선 SQL로 직접 페이징합니다. 여기서 ROW_NUMBER()라는 윈도우 함수를 씁니다.

board-mapper.xml — selectBoardList
<select id="selectBoardList" resultType="board">
    SELECT * FROM (
        SELECT ROW_NUMBER() OVER(ORDER BY b.bno DESC) AS rw, b.*
        FROM board_view b
    ) bv
    WHERE CEIL(bv.rw / #{size}) = #{page}
</select>
🟩 동작 순서
  1. board_view에서 게시글을 가져온다
  2. 게시글 번호 내림차순 정렬 (최신 글이 위로)
  3. ROW_NUMBER()로 각 행에 1, 2, 3… 순번(rw)을 붙인다
  4. 순번을 size로 나눈 뒤 CEIL(올림)
  5. 그 값이 요청한 page와 같은 행만 반환
🟨 알고리즘이 왜 맞는가 (예시)

size=20, page=2라면 → 순번 21~40번 행은 CEIL(21/20)=2 ... CEIL(40/20)=2로 모두 2가 됩니다. 그래서 “2페이지 = 21~40번” 행만 깔끔히 걸러집니다. 순번 1~20은 CEIL이 1, 41~60은 3이 되어 제외됩니다.

🟦 ROW_NUMBER() OVER(...)

조회된 각 행에 “몇 번째 줄인지” 번호를 매기는 함수입니다. OVER(ORDER BY ...)로 어떤 순서로 번호를 매길지 정합니다. 여기선 글 번호 내림차순이라 최신 글이 1번을 받습니다.

⬜ 다른 방법

MySQL에서는 보통 LIMIT #{size} OFFSET #{offset}가 더 간단하고 흔합니다. 다만 데이터가 아주 뒤쪽 페이지로 갈수록 OFFSET 방식은 느려질 수 있어, 대용량에선 “마지막으로 본 id 이후부터 가져오기(키셋 페이징)”를 씁니다.

검색 SQL & SQL Injection 주의

board-mapper.xml — searchBoardList
<select id="searchBoardList" resultType="board">
    SELECT * FROM (
        SELECT ROW_NUMBER() OVER(ORDER BY b.bno DESC) AS rw, b.*
        FROM board_view b
        WHERE b.title   LIKE CONCAT('%', #{keyword}, '%')
           OR b.content LIKE CONCAT('%', #{keyword}, '%')
    ) bv
    WHERE CEIL(bv.rw / #{size}) = #{page}
</select>

검색은 제목(title)과 본문(content) 두 곳을 봅니다. GET /api/posts?keyword=스프링 → title LIKE '%스프링%' OR content LIKE '%스프링%'.

🟥 #{} vs ${} — 보안 핵심

커밋 코드 일부엔 CEIL(bv.rw / ${size})처럼 ${}가 쓰였습니다. 차이는 결정적입니다:

  • #{size} → PreparedStatement 파라미터 바인딩. 값이 안전하게 분리되어 들어감 (권장)
  • ${size} → 문자열을 그대로 SQL에 끼워넣음. 외부 입력이 들어오면 SQL Injection 위험

숫자라도 외부 요청값이라면 가능한 한 #{}를 쓰세요.

🟦 SQL Injection이 뭔가요?

사용자가 입력칸에 ' OR 1=1 -- 같은 SQL 조각을 넣어, 의도하지 않은 쿼리를 실행시키는 공격입니다. #{}(바인딩)를 쓰면 입력이 “데이터”로만 취급되어 이런 공격이 통하지 않습니다.

boardCount

PaggingVO — 페이지 번호 계산

🟦 VO란?

VO(Value Object)는 “값을 담아 전달하는 객체”입니다. PaggingVO는 게시판 하단의 1 2 3 … 페이지 번호 버튼을 그리기 위한 계산 결과를 담습니다.

PaggingVO.java (핵심)
private int count;          // 전체 글 개수
private int currentPage;    // 현재 페이지
private final int PAGE_CONTENT_COUNT = 30;  // 한 페이지 글 수
private final int PAGE_GROUP_COUNT   = 5;   // 한 그룹 페이지 수

public int getTotalPage() {                 // 전체 페이지 수
    return count / PAGE_CONTENT_COUNT
         + (count % PAGE_CONTENT_COUNT != 0 ? 1 : 0);
}
🟩 전체 페이지 수 계산 (올림 나눗셈)

글 61개, 페이지당 30개라면 → 61 / 30 = 2, 나머지(1)가 있으니 +1 → 총 3페이지. “나머지가 있으면 한 페이지 더”가 핵심 아이디어입니다.

페이지 그룹 = 번호 버튼 묶음 1그룹: 1~5 2그룹: 6~10 3그룹: 11~15 시작 = (그룹번호-1)*5 + 1 끝 = min(전체페이지, 그룹번호*5) ← 끝은 전체 페이지를 넘지 않게
🟥 size 불일치 버그

Controller 기본 size=20인데, PaggingVO는 PAGE_CONTENT_COUNT=30으로 고정 계산합니다. SQL은 20개씩 가져오는데 페이지 수는 30개 기준이라 페이지 번호가 어긋납니다.

🟩 해결 — size를 넘겨 통일
public PaggingVO(int count, int currentPage, int size) {
    this.count = count;
    this.currentPage = currentPage;
    this.pageContentCount = size;   // 고정값 대신 실제 size 사용
}

flush() — 중복 로그인 오류 해결

🟦 무슨 문제였나

같은 사용자가 다시 로그인하면 “이미 있는 Refresh Token을 지우고 새로 저장”해야 합니다. 그런데 refresh_tokens.user_id가 UNIQUE라, 지우기도 전에 새로 넣으려다 중복키 충돌이 났습니다.

문제가 된 코드 (개념)
refreshTokenRepository.deleteByUser(user);   // 삭제 "예약"
RefreshToken token = new RefreshToken();
token.setUser(user);
refreshTokenRepository.save(token);          // 곧바로 INSERT 시도 → 충돌!
🟩 원인 — JPA의 지연 실행

JPA는 효율을 위해 SQL을 모았다가 트랜잭션 끝에 한꺼번에 보냅니다. 그래서 delete가 실제 DB에 반영되기 전에 insert가 먼저 나갈 수 있고, 그 순간 같은 user_id가 두 개가 되어 UNIQUE 충돌이 납니다.

수정 — flush()로 순서 보장
refreshTokenRepository.deleteByUser(user);
refreshTokenRepository.flush();              // ← DELETE를 "지금 즉시" DB에 반영

RefreshToken token = new RefreshToken();
token.setToken(refreshToken);
token.setUser(user);
token.setExpiresAt(LocalDateTime.now().plusDays(7));
refreshTokenRepository.save(token);          // 그 다음 INSERT → 안전
🟨 flush()의 의미

flush() = “지금까지 모아둔 변경(여기선 DELETE)을 즉시 DB에 SQL로 내보내라”. 실행 순서를 강제해 DELETE → INSERT 순으로 확실히 처리합니다. 트랜잭션을 끝내는 commit과는 다릅니다(트랜잭션은 계속 유지).

⬜ 다른 방법

아예 “있으면 갱신, 없으면 삽입(UPSERT)”으로 설계하거나, 기존 토큰을 찾아 토큰 값만 업데이트(Dirty Checking)하면 delete+insert 자체가 필요 없어 더 깔끔합니다.

Swagger + JWT 인증

🟦 Swagger가 뭔가요?

코드를 보고 API 문서를 자동으로 만들어 주고, 브라우저에서 바로 테스트까지 하게 해주는 도구입니다. Postman을 따로 안 켜도 “이 API는 뭘 받고 뭘 주는지” 확인하고 호출할 수 있습니다.

SwaggerConfig.java (요약)
@Bean
public OpenAPI openAPI() {
    String name = "JWT";
    return new OpenAPI()
        .info(new Info().title("Board API")
                        .description("게시판 백엔드 API 문서").version("v1"))
        .addSecurityItem(new SecurityRequirement().addList(name))
        .components(new Components().addSecuritySchemes(name,
            new SecurityScheme()
                .name(name).type(SecurityScheme.Type.HTTP)
                .scheme("bearer").bearerFormat("JWT")));
}
🟩 JWT 설정을 넣는 이유

이 설정 덕분에 Swagger 화면에 Authorize 버튼이 생깁니다. 로그인으로 받은 Access Token을 거기에 한 번 넣어두면, 이후 인증이 필요한 API들도 자동으로 Authorization: Bearer ... 헤더를 붙여 테스트할 수 있습니다.

접속 주소: http://localhost:8888/swagger-ui/index.html
🟥 Swagger 경로도 공개해야 함

SecurityConfig에서 /swagger-ui/**, /v3/api-docs/**를 permitAll()로 열어두지 않으면, 문서 화면 자체가 로그인에 막혀 안 보입니다.
