02B

인증과 인가

📘 개념 정리
  • 인증(Authentication): 사용자가 누구인지 확인하는 것
  • 인가(Authorization): 인증된 사용자가 해당 기능을 쓸 수 있는지 확인하는 것

로그인은 인증이고, 로그인한 사용자만 글을 작성하게 막는 것은 인가입니다.

📘 실생활 비유

회사 건물에 들어갈 때 사원증을 보여주는 것이 인증입니다. 사원증으로 들어왔어도 서버실에는 못 들어가게 막는 것이 인가입니다. JWT는 사원증, SecurityConfig의 URL 규칙은 출입 구역 표시판입니다.

HTTP 상태의미예시
401 Unauthorized로그인 정보 없음 또는 토큰 잘못됨토큰 없이 글쓰기 시도
403 Forbidden로그인은 했지만 권한 없음남의 글 수정·삭제 시도
404 Not Found대상 글·댓글이 없음삭제된 글 번호로 요청
02C

회원가입·로그인·로그인 이후 요청 흐름

회원가입 흐름

POST /auth/signup → AuthController → AuthService.signup() → 아이디 중복 검사 → BCrypt로 비밀번호 해시 → UserRepository.save()
💡 BCrypt 줄별 해설

PasswordEncoder.encode() 결과만 DB에 저장합니다. BCrypt는 단방향 해시이므로 원래 비밀번호를 복호화하지 않고 matches()로 일치 여부만 검사합니다. 같은 비밀번호도 매번 다른 해시가 생성되어 레인보우 테이블 공격을 어렵게 만듭니다.

로그인 흐름

POST /auth/login → AuthenticationManager.authenticate() → UserDetailServiceImpl이 DB 회원 조회 → PasswordEncoder가 비밀번호 비교 → AuthService가 Access/Refresh Token 생성 → Refresh Token DB 저장 → 토큰 두 개를 JSON으로 응답
📘 왜 AuthenticationManager를 쓰나?

서비스가 직접 비밀번호를 비교하지 않고 Spring Security의 표준 인증 절차를 이용하기 위해서입니다. 검증 로직이 한곳에 모여 있어 유지보수가 쉽습니다.

로그인 이후 요청 흐름

React 요청 → Authorization 헤더 → JwtAuthenticationFilter → JwtTokenProvider.validateToken() → 토큰의 username으로 DB 회원 조회 → SecurityContextHolder에 Authentication 저장 → URL 권한 검사 → Controller
Controller에서 현재 회원 받기
@AuthenticationPrincipal UserEntity currentUser
⚠️ 작성자 번호를 프론트가 보낸 값으로 믿으면 안 됨

게시글·댓글 등록 시 프론트가 보낸 mid를 그대로 쓰면 다른 회원 번호를 넣어 남의 이름으로 글을 쓸 수 있습니다. 서버가 JWT 인증 결과에서 회원을 꺼내 덮어씁니다.

board.setMid(currentUser.getId());
🔄 대안

세션 기반(step14)은 서버가 로그인 상태를 기억합니다. JWT는 클라이언트가 토큰을 들고 다닙니다. 모바일 앱·React SPA·마이크로서비스에는 JWT가 더 흔하고, 전통적인 서버 렌더링 사이트에는 세션이 여전히 쓰입니다.

02D

React에서 JWT 사용하기 (step15-front)

📘 왜 프론트에서 토큰을 저장하나?

백엔드는 STATELESS라 "이 사람 로그인했음"을 기억하지 않습니다. React가 매 API 호출마다 Authorization: Bearer ... 헤더를 붙여야 합니다.

① 토큰 저장

localStorage.setItem("accessToken", token);
⚠️ localStorage의 함정

새로고침 후에도 유지되어 학습용으로 편하지만, XSS 공격이 발생하면 JavaScript가 토큰을 읽을 수 있습니다. 운영 환경에서는 Secure + HttpOnly 쿠키 방식도 검토해야 합니다.

② 보호된 API 호출

axios.get(url, {
  headers: {
    Authorization: `Bearer ${accessToken}`
  }
});
💡 Bearer 뒤 공백 한 칸

Bearer 뒤에 공백 한 칸이 반드시 필요합니다. 백엔드 필터는 "Bearer "로 시작하는지 확인한 뒤 앞의 7글자를 제거합니다.

③ CORS

📘 실생활 비유

React(localhost:3000)와 Spring(localhost:8888)은 포트가 달라 브라우저가 다른 출처로 판단합니다. 마치 다른 건물에 있는 창구에 서류를 내려면 "이 건물에서 온 사람 맞다"는 허가증(CORS 헤더)이 필요한 것과 같습니다.

🚀 요즘 트렌드

개발 중에는 Vite/Webpack 프록시로 같은 출처처럼 보이게 하거나, BFF(Backend For Frontend) 패턴으로 API 게이트웨이를 두기도 합니다.

02E

Google OAuth2 로그인 (Step16)

📘 OAuth2란?

"다른 서비스(구글)의 계정으로 우리 사이트에 로그인"하게 해주는 표준 방식입니다. 비밀번호를 우리 DB에 저장하지 않아도 됩니다.

OAuth2 전체 흐름 (10단계)

1. React에서 /oauth2/authorization/google 이동 2. Spring Security가 Google 로그인 화면으로 리다이렉트 3. 사용자가 Google 로그인과 정보 제공 승인 4. Google이 Authorization Code를 백엔드에 전달 5. Spring이 Code를 Google Access Token으로 교환 6. CustomOAuth2UserService가 Google 사용자 정보 조회 7. 최초 사용자면 우리 DB에 자동 회원가입 8. OAuth2SuccessHandler가 우리 서비스용 JWT 발급 9. React /oauth2/callback으로 리다이렉트 10. React가 JWT를 저장하고 이후 API 호출에 사용
⚠️ 두 토큰은 다르다!
  • Google Access Token: Google API에서 사용자 정보를 가져올 때 사용
  • 자체 JWT: 우리 Spring Boot API의 인증에 사용

Google에서 받는 주요 속성

속성의미
subGoogle 계정의 안정적인 고유 ID
email이메일
name표시 이름
picture프로필 이미지 URL

DB 설계 & board.sql

📘 테이블 구조 개요

게시판에 필요한 테이블은 5개입니다. 회원, 게시글, 댓글, 게시글 반응(좋아요), 댓글 반응, 그리고 JWT 리프레시 토큰 저장용.

board_member (회원) ↓ 1:N board (게시글) board_reaction (게시글 좋아요/싫어요) ↓ 1:N └── mid → board_member.id board_comment (댓글) board_comment_reaction (댓글 반응) └── mid → board_member.id refresh_tokens (JWT 리프레시 토큰) └── user_id → board_member.id (1:1)

외래키 & CASCADE 설정

🟢 CASCADE란

ON DELETE CASCADE를 설정하면 부모 데이터 삭제 시 자식 데이터도 자동으로 삭제됩니다. 게시글을 삭제하면 댓글과 반응도 함께 삭제됩니다.

-- 게시글 삭제 시 댓글 자동 삭제
ALTER TABLE board_comment
  ADD CONSTRAINT FK_board_TO_board_comment
    FOREIGN KEY (bno) REFERENCES board(bno) ON DELETE CASCADE;

-- 게시글 삭제 시 반응 자동 삭제
ALTER TABLE board_reaction
  ADD CONSTRAINT FK_board_TO_board_reaction
    FOREIGN KEY (bno) REFERENCES board(bno) ON DELETE CASCADE;

-- 한 사람이 같은 게시글에 반응 1개만 가능 (UNIQUE 제약)
ALTER TABLE board_reaction ADD CONSTRAINT UNIQUE (mid, bno);
ALTER TABLE board_comment_reaction ADD CONSTRAINT UNIQUE (mid, cno);

VIEW 정의 (MySQL 8.0 WITH CTE)

💡 VIEW란

여러 테이블을 미리 JOIN해서 "가상 테이블"처럼 만들어 놓은 것입니다. board_view는 게시글에 닉네임·좋아요수·싫어요수를 합쳐서 보여줍니다.

CREATE OR REPLACE VIEW board_view AS
WITH board_content_like AS (
  SELECT bno, count(*) AS blike FROM board_reaction WHERE type = 'like' GROUP BY bno
),
board_content_hate AS (
  SELECT bno, count(*) AS bhate FROM board_reaction WHERE type = 'dislike' GROUP BY bno
)
SELECT
  b.bno, b.title, b.write_date, b.write_update_date,
  b.content, b.bcount, bm.id AS mid, bm.nickname,
  IFNULL(bcl.blike, 0) AS blike,
  IFNULL(bch.bhate, 0) AS bhate
FROM board b
LEFT JOIN board_member bm ON b.mid = bm.id
LEFT JOIN board_content_like bcl ON bcl.bno = b.bno
LEFT JOIN board_content_hate bch ON bch.bno = b.bno;
🟢 View를 사용한 이유
board + board_member + 게시글 LIKE 집계 + 게시글 DISLIKE 집계 = board_view

Java 코드에서 복잡한 조인과 집계 SQL을 반복하지 않는 장점이 있습니다. 반면 View 정의가 바뀌면 이를 사용하는 모든 쿼리에 영향을 주므로 DB 스키마도 코드처럼 버전 관리해야 합니다.

🔄 대안

View 대신 MyBatis XML에 JOIN·집계를 직접 쓰거나, JPA에서 @Query로 네이티브 SQL을 작성할 수도 있습니다. 팀에서 SQL 가독성과 재사용성 중 무엇을 우선할지 정하면 됩니다.

MyBatis XML Mapper

📘 MyBatis란

Java와 SQL을 연결해주는 프레임워크입니다. SQL을 XML 파일에 따로 작성하고, Java 인터페이스(Mapper)와 연결합니다. JPA보다 SQL을 직접 제어할 수 있어 복잡한 쿼리에 유리합니다.

Step17은 JPA(회원·Refresh Token)와 MyBatis(게시글·댓글)를 함께 씁니다. JPA가 있다고 모든 테이블을 JPA로 처리할 필요는 없습니다.

BoardMapper.java (인터페이스) ←→ board-mapper.xml (SQL) selectBoardList() SELECT ... FROM board_view ... insertBoard() INSERT INTO board ... selectBoardReaction() SELECT ... FROM board_reaction ...

board-mapper.xml

src/main/resources/mappers/board-mapper.xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
  "https://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.spring.mapper.BoardMapper">

  <!-- 페이징 목록: ROW_NUMBER()로 페이지 번호 기준 조회 -->
  <select id="selectBoardList" resultType="board">
    SELECT * FROM (
      SELECT ROW_NUMBER() OVER(ORDER BY b.bno DESC) AS rw, b.*
      FROM board_view b
    ) bv
    WHERE CEIL(bv.rw / #{size}) = #{page}
  </select>

  <!-- 검색 + 페이징 (${size} 주의: $ 는 SQL Injection 위험 있음) -->
  <select id="searchBoardList" resultType="board">
    SELECT * FROM (
      SELECT ROW_NUMBER() OVER(ORDER BY b.bno DESC) AS rw, b.*
      FROM board_view b
      WHERE b.title LIKE CONCAT('%',#{keyword},'%')
        OR b.content LIKE CONCAT('%',#{keyword},'%')
    ) bv
    WHERE CEIL(bv.rw / ${size}) = #{page}
  </select>

  <!-- useGeneratedKeys: INSERT 후 생성된 AUTO_INCREMENT 값을 board.bno에 자동 설정 -->
  <insert id="insertBoard" useGeneratedKeys="true" keyProperty="bno">
    INSERT INTO board(title, content, mid)
    VALUES(#{title}, #{content}, #{mid})
  </insert>

  <select id="selectBoardReaction" resultType="boardReq">
    SELECT * FROM board_reaction WHERE mid = #{id} AND bno = #{bno}
  </select>

  <select id="selectBoardReactionCount" resultType="reaction">
    SELECT
      COUNT(CASE WHEN br.type = 'like' THEN 1 END) AS likeCount,
      COUNT(CASE WHEN br.type = 'dislike' THEN 1 END) AS dislikeCount
    FROM board b
    LEFT OUTER JOIN board_reaction br ON b.bno = br.bno
    WHERE b.bno = #{bno}
  </select>
</mapper>
⚠️ #{} vs ${} 차이
  • #{keyword} — PreparedStatement 파라미터. SQL Injection 안전. 대부분 이걸 씁니다.
  • ${size} — 값을 그대로 SQL에 삽입. 숫자·고정값에만 씁니다. 사용자 입력에 쓰면 SQL Injection 위험!

현재 검색 쿼리에 ${size}가 한 군데 있습니다. 숫자 매개변수라 바로 문제가 드러나지 않을 수 있지만, 원칙적으로 외부 입력에는 #{}를 사용해야 합니다.

Spring Security 설정 (SecurityConfig)

📘 Spring Security란

로그인/로그아웃, URL 접근 권한, 비밀번호 암호화 등 보안 관련 기능을 담당하는 프레임워크입니다. 이 프로젝트는 세션 대신 JWT를 사용하므로 STATELESS 모드로 설정합니다.

SecurityConfig.java
@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

  private final JwtAuthenticationFilter jwtAuthenticationFilter;

  @Bean
  public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())          // REST API는 CSRF 불필요
        .cors(cors -> cors.configurationSource(corsConfigrationSource()))
        .sessionManagement(sm ->
            sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))  // 세션 사용 안 함
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/auth/**").permitAll()          // 로그인·회원가입 누구나
            .requestMatchers("/v3/api-docs/**").permitAll()   // Swagger 문서
            .requestMatchers("/swagger-ui.html").permitAll()
            .requestMatchers("/swagger-ui/**").permitAll()
            .requestMatchers(HttpMethod.GET, "/api/posts/**").permitAll()  // 글 조회 누구나
            .anyRequest().authenticated())                    // 그 외 로그인 필요
        .addFilterBefore(jwtAuthenticationFilter,
            UsernamePasswordAuthenticationFilter.class);      // JWT 필터 먼저 실행
    return http.build();
  }

  @Bean
  public CorsConfigurationSource corsConfigrationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("http://localhost:3000"));  // React 주소
    config.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE","OPTIONS"));
    config.setAllowedHeaders(List.of("*"));
    config.setAllowCredentials(true);
    config.setMaxAge(3600L);  // Preflight 1시간 캐시
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
  }

  @Bean
  public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();  // 비밀번호 단방향 해시
  }

  @Bean
  public AuthenticationManager authenticationManager(
      AuthenticationConfiguration config) throws Exception {
    return config.getAuthenticationManager();
  }
}

JWT 토큰 생성·검증 (JwtTokenProvider)

📘 JWT(JSON Web Token)란

사용자 정보를 서버가 저장하지 않고 암호화된 토큰에 담아 클라이언트가 들고 다니는 방식입니다. 모든 요청마다 토큰을 Header에 넣어 보내면 서버가 검증합니다.

JWT 구조: Header.Payload.Signature eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJ1c2VyMSJ9 . xxxx ↑ 알고리즘 ↑ 사용자정보(claims) ↑ 서명(위변조 검증용)
토큰 종류만료용도
Access Token30분API 요청 시 Authorization 헤더에 첨부
Refresh Token7일Access Token 만료 시 재발급 요청에 사용
⚠️ Payload는 암호화가 아닙니다

JWT의 Payload는 Base64 형태라 누구나 내용을 볼 수 있습니다. 비밀번호나 주민번호 같은 민감 정보는 절대 넣으면 안 됩니다. Signature는 위변조 방지만 보장합니다.

📘 Access Token 헤더 형식
Authorization: Bearer eyJ...

Refresh Token은 DB에도 저장합니다. 로그아웃 시 삭제하거나 서버에서 강제로 재발급을 막을 수 있습니다.

JwtTokenProvider.java
@Component
public class JwtTokenProvider {
    private final SecretKey key;
    private final long accessExpiration;
    private final long refreshExpiration;

    public JwtTokenProvider(
        @Value("${jwt.secret}") String secret,       // application.properties에서 주입
        @Value("${jwt.access-expiration}") long accessExpiration,
        @Value("${jwt.refresh-expiration}") long refreshExpiration
    ) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes());  // 비밀키로 SecretKey 생성
        this.accessExpiration = accessExpiration;
        this.refreshExpiration = refreshExpiration;
    }

    // Access Token 생성: username + role + 만료시간을 토큰에 담음
    public String generateAccessToken(UserDetails userDetails) {
        return Jwts.builder()
            .subject(userDetails.getUsername())
            .claim("role", userDetails.getAuthorities().iterator().next().getAuthority())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + accessExpiration))
            .signWith(key)
            .compact();
    }

    // 토큰 검증: 파싱 가능하면 true, 만료·위변조시 false
    public boolean validateToken(String token) {
        try { parseClaims(token); return true; }
        catch (ExpiredJwtException | JwtException e) { return false; }
    }

    public Claims parseClaims(String token) {
        return Jwts.parser().verifyWith(key).build()
            .parseSignedClaims(token).getPayload();
    }

    public String getUsername(String token) { return parseClaims(token).getSubject(); }
}

JWT 인증 필터 (JwtAuthenticationFilter)

📘 필터란

모든 HTTP 요청이 Controller에 도달하기 전에 통과해야 하는 관문입니다. JwtAuthenticationFilter는 요청 헤더에서 JWT를 꺼내 검증하고, 유효하면 Spring Security의 인증 정보를 설정합니다.

클라이언트 요청 → JwtAuthenticationFilter.doFilterInternal() ├── Authorization 헤더 없음 → 그냥 통과 (비로그인 허용 URL은 정상 응답) ├── 토큰 있지만 유효하지 않음 → 그냥 통과 (이후 인가 단계에서 401) └── 토큰 유효 → SecurityContext에 인증 정보 저장 → 통과 → Controller
JwtAuthenticationFilter.java
@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtTokenProvider jwtTokenProvider;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
            HttpServletResponse response, FilterChain filterChain)
            throws ServletException, IOException {

        String header = request.getHeader("Authorization");

        // "Bearer " 로 시작하는 토큰만 처리
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);  // "Bearer " 제거

            if (jwtTokenProvider.validateToken(token)) {
                String username = jwtTokenProvider.getUsername(token);
                UserDetails userDetails = userDetailsService.loadUserByUsername(username);

                // Spring Security 인증 객체 생성 & 등록
                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(
                        userDetails, null, userDetails.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }

        filterChain.doFilter(request, response);  // 다음 필터로 전달
    }
}
💡 OncePerRequestFilter란

한 요청당 딱 한 번만 실행되는 필터 기반 클래스입니다. Spring 내부에서 같은 요청이 여러 번 필터를 거치는 경우를 방지합니다.

AuthService — 회원가입·로그인·로그아웃

@Service
@RequiredArgsConstructor
public class AuthService {
    private final UserRepository userRepository;
    private final RefreshTokenRepository refreshTokenRepository;
    private final PasswordEncoder passwordEncoder;
    private final JwtTokenProvider jwtTokenProvider;
    private final AuthenticationManager authenticationManager;

    // 회원가입: 아이디 중복 확인 + 비밀번호 BCrypt 암호화
    public UserEntity signup(SignupRequest req) {
        if (userRepository.existsByUsername(req.getUsername()))
            throw new RuntimeException("이미 사용 중인 아이디입니다.");
        UserEntity user = UserEntity.builder()
            .username(req.getUsername())
            .password(passwordEncoder.encode(req.getPassword()))  // 암호화!
            .nickname(req.getNickname())
            .build();
        return userRepository.save(user);
    }

    // 로그인: Spring Security가 비밀번호 비교 후 Access + Refresh Token 반환
    @Transactional
    public String[] login(String username, String password) {
        Authentication auth = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(username, password));
        UserEntity user = (UserEntity) auth.getPrincipal();
        String accessToken = jwtTokenProvider.generateAccessToken(user);
        String refreshToken = jwtTokenProvider.generateRefreshToken(user);
        saveRefreshToken(user, refreshToken);
        return new String[]{ accessToken, refreshToken };
    }

    // 로그아웃: DB에서 Refresh Token 삭제
    @Transactional
    public void logout(UserEntity user) {
        refreshTokenRepository.deleteByUser(user);
    }
}

        if (board.getMid() != userEntity.getId())
            return ResponseEntity.status(HttpStatus.FORBIDDEN).build(); // 403

        return ResponseEntity.noContent().build(); // 204

        BoardDTO board = boardService.selectBoard(bno);
        if (board.getMid() != userEntity.getId())
            return ResponseEntity.status(HttpStatus.FORBIDDEN).build();
        reqBoard.setBno(bno);

좋아요/싫어요 토글 알고리즘

📘 토글 알고리즘 개요

좋아요/싫어요 버튼을 누를 때 3가지 경우가 있습니다. 같은 타입을 누르면 취소, 다른 타입을 누르면 변경, 처음 누르면 추가.

버튼 클릭 (type: 'like' 또는 'dislike') ↓ DB에서 이 사용자의 기존 반응 조회 ├── 기존 반응 없음 → INSERT (새로 추가) ├── 같은 타입 클릭 → DELETE (취소 — 토글 off) └── 다른 타입 클릭 → UPDATE type (좋아요→싫어요 또는 반대) ↓ 최신 likeCount / dislikeCount 조회 후 응답 { count: { likeCount: 5, dislikeCount: 2 } }
BoardController.java — boardReaction()
@PostMapping("/reaction")
public ResponseEntity<Map<String,Object>> boardReaction(
    @RequestBody BoardReactionReq reactionReq,
    @AuthenticationPrincipal UserEntity userEntity
) {
    // 이 사용자의 기존 반응 조회
    BoardReactionReq req = boardService.selectBoardReaction(
        reactionReq.getBno(), userEntity.getId());

    if (req == null) {
        // 처음 누름 → INSERT
        reactionReq.setMid(userEntity.getId());
        boardService.addBoardReaction(reactionReq);
    } else {
        reactionReq.setId(req.getId());
        if (reactionReq.getType().equals(req.getType()))
            boardService.deleteBoardReaction(reactionReq);  // 같은 타입 → 취소
        else
            boardService.updateBoardReaction(reactionReq);  // 다른 타입 → 변경
    }

    ReactionCountDTO reactionCount = boardService.getBoardReactionCount(reactionReq.getBno());
    return ResponseEntity.ok(Map.of("count", reactionCount));
}
💡 UNIQUE 제약이 중요한 이유

board_reaction 테이블에 UNIQUE(mid, bno)를 걸어두면 같은 사람이 같은 게시글에 반응을 2개 넣으려 하면 DB가 오류를 냅니다. 코드 버그로 중복 INSERT가 발생해도 데이터가 오염되지 않습니다.

PaggingVO 페이징 계산 알고리즘

📘 페이징이란

게시글 전체를 한 번에 보여주면 느리고 보기 불편합니다. 30개씩 나눠서 1페이지, 2페이지… 로 보여주는 것을 페이징이라고 합니다.

public class PaggingVO {
    private int count;         // 전체 게시글 수
    private int currentPage;   // 현재 페이지
    private final int PAGE_CONTENT_COUNT = 30;  // 페이지당 게시글 수 (고정)
    private final int PAGE_GROUP_COUNT = 5;     // 하단 페이지 번호 개수 (고정)

    public PaggingVO(int count, int currentPage) {  // 2인자 생성자
        this.count = count;
        this.currentPage = currentPage;
    }

    // 전체 페이지 수
    public int getTotalPage() {
        return count / PAGE_CONTENT_COUNT + (count % PAGE_CONTENT_COUNT != 0 ? 1 : 0);
    }

    // 현재 그룹 번호 (페이지 7 → 2번째 그룹)
    public int getCurrentPageGroupNo() {
        return currentPage / PAGE_GROUP_COUNT + (currentPage % PAGE_GROUP_COUNT != 0 ? 1 : 0);
    }

    // 현재 그룹의 시작 페이지 (2번째 그룹 → 6페이지)
    public int getStartPageOfPageGroup() {
        return (getCurrentPageGroupNo() - 1) * PAGE_GROUP_COUNT + 1;
    }

    // 현재 그룹의 끝 페이지 (마지막 페이지 초과 불가)
    public int getEndPageOfPageGroup() {
        return Math.min(getTotalPage(), getCurrentPageGroupNo() * PAGE_GROUP_COUNT);
    }

    public boolean isPriviousPageGroup() { return getCurrentPageGroupNo() > 1; }
    public boolean isNextPageGroup() { return getCurrentPageGroupNo() < getTotalPageGroup(); }
}

상황계산결과
전체 92개, 페이지당 30개92/30=3 나머지 2 → 3+1totalPage = 4
현재 페이지 7, 그룹당 5개7/5=1 나머지 2 → 1+1currentGroup = 2

⚠️ size 불일치 버그 (자주 틀리는 부분)

Controller는 요청의 기본 size를 20으로 받지만 PaggingVO는 한 페이지 크기를 30으로 고정합니다. 목록 SQL과 페이지 계산의 크기가 달라질 수 있으므로, size를 PaggingVO 생성자에도 전달하는 구조가 자연스럽습니다.

AuthContext (전역 인증 상태 관리)

📘 Context API란

React에서 여러 컴포넌트가 같은 데이터를 공유할 때 사용하는 기능입니다. 로그인 정보는 NavBar, PostDetailPage 등 여러 곳에서 필요하므로 Context로 전역 관리합니다.

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);     // 로그인한 사용자 정보
  const [loading, setLoading] = useState(true);

  // 앱 시작 시: localStorage에 토큰이 있으면 /auth/me로 사용자 정보 복원
  useEffect(() => {
    const token = localStorage.getItem('accessToken');
    if (token) {
      authApi.me()
        .then(res => setUser(res.data))
        .catch(() => localStorage.clear())   // 토큰 만료 시 클리어
        .finally(() => setLoading(false));
    } else {
      setLoading(false);
    }
  }, []);

  const login = async (username, password) => {
    const loginRes = await authApi.login({ username, password });
    localStorage.setItem('accessToken', loginRes.data.accessToken);    // 브라우저 저장
    localStorage.setItem('refreshToken', loginRes.data.refreshToken);
    const meRes = await authApi.me();
    setUser(meRes.data);                     // 전역 상태 업데이트
    return meRes.data;
  };

  const logout = async () => {
    try { await authApi.logout(); } catch {}
    localStorage.clear();
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, loading, isAuthenticated: !!user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

export const useAuth = () => {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth는 AuthProvider에서만 사용 가능합니다');
  return ctx;  // { user, loading, isAuthenticated, login, logout }
};

📘 Axios란

브라우저에서 HTTP 요청을 보내는 라이브러리입니다. 기본 fetch보다 사용하기 쉽고, 인터셉터(요청 가로채기) 기능이 있습니다.

import axios from "axios";

const API_URL = process.env.REACT_APP_API_URL || 'http://localhost:8888';

const axiosInstance = axios.create({
  baseURL: API_URL,                          // 모든 요청의 기본 URL
  headers: { 'Content-Type': 'application/json' }
});

// 요청 인터셉터: 모든 요청에 JWT 자동 첨부
axiosInstance.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem("accessToken");
    if (token) config.headers.Authorization = `Bearer ${token}`;
    return config;
  },
  (error) => Promise.reject(error)
);

export default axiosInstance;
🟢 인터셉터 동작

모든 API 파일에서 axios.create()를 직접 쓰면 baseURL을 일일이 지정해야 합니다. axiosInstance를 하나 만들어 공유하면 baseURL 변경 시 한 곳만 바꾸면 됩니다.

텍스트를 굵게, 이탤릭, 헤딩, 목록, 이미지 삽입 등을 할 수 있는 리치 텍스트 에디터 라이브러리입니다. 설치: npm install quill

useRef 3개 패턴

useRef역할왜 useRef?
editorRefQuill이 렌더링될 DOM 컨테이너DOM에 직접 접근해야 하므로
quillInstanceQuill 인스턴스 보관리렌더링해도 인스턴스가 사라지지 않게
onChangeRef최신 onChange 함수 참조클로저 문제 방지 (오래된 함수 참조 방지)
export default ({ onChange, defaultValue }) => {
  const editorRef = useRef(null);
  const quillInstance = useRef(null);
  const onChangeRef = useRef(onChange);
  const initializedRef = useRef(false);  // 수정 모드: 초기값 1회만 설정

  onChangeRef.current = onChange;  // 리렌더링마다 최신 onChange 반영

  // Quill 인스턴스는 최초 1회만 생성
  useEffect(() => {
    if (editorRef.current && !quillInstance.current) {
      quillInstance.current = new Quill(editorRef.current, {
        theme: "snow",
        modules: { toolbar: [["bold","italic","underline"], ["link","image"], ...] }
      });

      quillInstance.current.on("text-change", () => {
        if (onChangeRef.current)
          onChangeRef.current(quillInstance.current.getSemanticHTML());
      });
    }
  }, []);  // 빈 배열 = 마운트 시 1회만

  // 수정 모드: defaultValue가 도착했을 때 1회만 초기값 설정
  useEffect(() => {
    if (quillInstance.current && defaultValue && !initializedRef.current) {
      quillInstance.current.root.innerHTML = defaultValue;
      initializedRef.current = true;
    }
  }, [defaultValue]);

  return (
    <div style={{ margin: "50px" }}>
      <div ref={editorRef} style={{ height: "500px" }}></div>
    </div>
  );
};
🟢 initializedRef가 필요한 이유

수정 모드에서 API로 기존 게시글을 불러온 후 Quill에 초기값을 설정할 때, defaultValue가 바뀔 때마다 실행되면 사용자가 편집 중인 내용이 덮어써집니다. initializedRef를 true로 설정해 최초 1회만 초기화합니다.

⚠️ key 패턴 (PostWritePage에서)

<QuillEditor key={bno || "create"} />처럼 key를 다르게 주면 React가 컴포넌트를 완전히 재생성합니다. 수정 모드↔작성 모드를 전환할 때 Quill을 새로 초기화하기 위해 사용합니다.

export default ({ pagging, onPageChange }) => {
  // 현재 그룹의 시작~끝 페이지 번호 배열 생성
  const pageNumbers = [];
  for (let i = pagging.startPageOfPageGroup; i <= pagging.endPageOfPageGroup; i++)
    pageNumbers.push(i);

  return <ul>
    {/* 이전 그룹 버튼 */}
    <li>
      <button
        disabled={!pagging.priviousPageGroup}
        onClick={() => onPageChange(pagging.startPageOfPageGroup - 1)}>
        ◀◀
      </button>
    </li>

    {/* 페이지 번호 버튼들 */}
    {pageNumbers.map(item => (
      <li key={item}>
        <button
          onClick={() => onPageChange(item)}
          disabled={item === pagging.currentPage}>  {/* 현재 페이지는 비활성화 */}
          {item}
        </button>
      </li>
    ))}

    {/* 다음 그룹 버튼 */}
    <li>
      <button
        disabled={!pagging.nextPageGroup}
        onClick={() => onPageChange(pagging.endPageOfPageGroup + 1)}>
        ▶▶
      </button>
    </li>
  </ul>
}

게시글 작성/수정 페이지 (PostWritePage)

📘 한 컴포넌트, 두 가지 역할

URL에 :bno가 있으면 수정 모드, 없으면 작성 모드입니다. isEditorMode = !!bno로 분기합니다.

export default () => {
  const { bno } = useParams();
  const isEditorMode = !!bno;          // bno 있으면 수정 모드
  const navigate = useNavigate();
  const [form, setForm] = useState({ title: '', content: '' });
  const [loading, setLoading] = useState(false);

  // 수정 모드: 기존 게시글 데이터 불러오기
  useEffect(() => {
    if (!isEditorMode) return;
    postApi.getPost(bno).then(res => {
      setForm({
        title: res.data.board.title,
        content: res.data.board.content
      });
    });
  }, [bno, isEditorMode]);

  const handleSubmit = async () => {
    if (!form.title.trim() || !form.content.trim()) {
      alert('제목과 내용을 입력해 주세요'); return;
    }
    try {
      setLoading(true);
      if (isEditorMode) {
        await postApi.update(bno, form);          // PATCH → 204
        navigate(`/posts/${bno}`);
      } else {
        const res = await postApi.create(form);   // POST → { board: { bno, ... } }
        navigate(`/posts/${res.data.board.bno}`); // useGeneratedKeys로 받은 bno로 이동!
      }
    } finally { setLoading(false); }
  };

  return <div>
    <h2>{isEditorMode ? '게시글 수정' : '게시글 쓰기'}</h2>
    <input value={form.title} onChange={e => setForm(p => ({...p, title: e.target.value}))} />

    {/* key를 다르게 주면 수정↔작성 전환 시 QuillEditor 완전 재생성 */}
    <QuillEditor
      key={bno || "create"}
      onChange={content => setForm(p => ({...p, content}))}
      defaultValue={form.content}
    />

    <button onClick={handleSubmit} disabled={loading}>
      {loading ? '저장 중...' : (isEditorMode ? '수정하기' : '글쓰기')}
    </button>
    <button onClick={() => navigate(-1)}>취소</button>
  </div>;
}
💡 작성 후 새 게시글로 이동하는 원리

postApi.create(form)이 { board: { bno: 42, ... } }를 응답합니다. 이 bno: 42는 insertBoard useGeneratedKeys가 MySQL AUTO_INCREMENT 값을 Java 객체에 자동 설정한 것입니다. 덕분에 navigate(`/posts/42`)로 새 글 상세 페이지로 바로 이동합니다.

CORS 설정

📘 CORS란

Cross-Origin Resource Sharing. 브라우저는 보안상 출처(origin)가 다른 서버에 기본적으로 요청을 차단합니다. React(localhost:3000)에서 Spring Boot(localhost:8888)로 요청할 때 포트가 달라 다른 출처가 됩니다. 서버가 명시적으로 허용해야 합니다.

브라우저 (localhost:3000) → POST http://localhost:8888/api/posts ↓ 브라우저가 먼저 Preflight 요청을 보냄 OPTIONS http://localhost:8888/api/posts Origin: http://localhost:3000 서버 (localhost:8888) ← 응답 헤더: Access-Control-Allow-Origin: http://localhost:3000 Access-Control-Allow-Methods: GET,POST,PATCH,DELETE,OPTIONS Access-Control-Allow-Credentials: true ↓ 브라우저: "허용된 출처다" → 실제 POST 요청 전송
SecurityConfig.java — corsConfigrationSource()
config.setAllowedOrigins(List.of("http://localhost:3000"));  // React 주소만 허용
config.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE","OPTIONS"));
config.setAllowedHeaders(List.of("*"));       // 모든 헤더 허용
config.setAllowCredentials(true);             // Authorization 헤더 허용
config.setMaxAge(3600L);                      // OPTIONS 응답 1시간 캐시 (Preflight 줄이기)
⚠️ 실서비스에서는

운영 서버 배포 시 setAllowedOrigins를 실제 도메인으로 바꿔야 합니다. http://localhost:3000을 그대로 두면 서비스가 동작하지 않습니다.

🔄 @CrossOrigin 어노테이션 방법

Controller 클래스에 @CrossOrigin(origins = "http://localhost:3000")를 붙이는 방법도 있습니다. 하지만 Controller마다 붙여야 해서 번거롭고, SecurityConfig에서 한 번에 관리하는 것이 더 좋습니다.

요즘 트렌드

🚀 Next.js

React 기반의 풀스택 프레임워크입니다. 서버 사이드 렌더링(SSR), 정적 생성(SSG), API Routes를 한 프로젝트에서 처리할 수 있습니다. SEO가 중요한 서비스나 빠른 초기 로딩이 필요할 때 사용합니다. 현재 React 앱의 자연스러운 다음 단계입니다.

🚀 TanStack Query (React Query)

서버 상태 관리 라이브러리입니다. useEffect + useState로 API 호출하던 패턴을 useQuery, useMutation으로 대체합니다. 캐싱, 자동 재조회, 로딩/에러 상태 처리를 자동으로 해줍니다.

// 기존 방식
useEffect(() => {
  postApi.getPage(1).then(res => setPosts(res.data.list));
}, []);

// TanStack Query
const { data, isLoading } = useQuery({
  queryKey: ['posts', page],
  queryFn: () => postApi.getPage(page).then(r => r.data)
});
🚀 Zustand

간단한 전역 상태 관리 라이브러리입니다. Context API보다 코드가 적고 성능이 좋습니다. AuthContext를 Zustand로 대체하면 코드가 훨씬 간결해집니다.

🚀 Docker

앱과 그 실행 환경을 컨테이너로 패키징해 어디서든 같은 환경으로 실행하는 기술입니다. "내 컴퓨터에서는 됐는데 서버에서 안 된다"는 문제를 해결합니다. Spring Boot와 MySQL을 Docker Compose로 한 번에 실행할 수 있습니다.

🚀 MSW (Mock Service Worker)

브라우저에서 API 요청을 가로채 가짜 응답을 돌려주는 테스트 도구입니다. 백엔드 없이 프론트를 개발하거나 테스트할 때 유용합니다.
